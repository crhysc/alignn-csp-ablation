# alignn-csp-ablation

Ablation suites for ALIGNN-CSP's generative inverse-design pipeline, run in
support of the ALIGNN 2.0 manuscript.

## State of the project, and how to restore it

**Start with [`PROJECT_STATE.md`](PROJECT_STATE.md).** It is the entry point
for anyone new: what exists, where every artifact lives (GitHub, Hugging Face,
DVC), the results so far, the pitfalls, and how to pull the whole state onto a
new machine. The one open job is in [`NEXT_TASK.md`](NEXT_TASK.md).

Each harness directory carries an `EXPERIMENT_SET.yaml` (the experiment set's
full context) and, under every `results/<dataset>/<run_id>/ablations/`, one
exhaustive YAML per ablation run plus an `INDEX.md`. Bulk artifacts (weights,
predictions, histories, GPU traces, datasets) are DVC-tracked and mirrored to
Hugging Face; `bash tools/hf_sync.sh pull` restores them.

## Layout

```
alignn/                                                    <- submodule: crhysc/alignn @ angle-diffusion
                                                                the model: diffusion, ablations, angles, sampling

supercon-alex-bond-angle-diffusion-ablation-sep-2-2026/     <- harness: the A0-A6 angular-diffusion suite
                                                                (does explicit bond-angle denoising help, and why)

supercon-alex-bond-angle-diffusion-line-graph-ablations-sep-2-2026/
                                                             <- harness: line graph x bond-angle diffusion, a 2x2
                                                                (does either factor still help without the other)

install.sh                                                  <- portable setup: envs, submodule, AtomBench
site.env                                                    <- (generated by install.sh; not tracked) this site's paths
HANDOFF.md                                                  <- narrative account of the first cluster move
```

Each harness directory is self-contained: its own `env.sh` (single source of
truth for its paths and scheduler settings), its own numbered run scripts
(`00_setup.sh`, `10_smoke.sh`, ...), and its own `README.md` and `PLAN.md`
(the design document — read that one first, in whichever harness you're
using). The two harnesses are independent by design — separate run trees,
separate config-name prefixes — precisely so neither can collide with or be
confused for the other; see either harness's `PLAN.md` for why they exist as
two harnesses rather than one.

## Setting this up on a new machine or cluster

```bash
git clone --recurse-submodules <this repo>
cd alignn-csp-ablation
bash install.sh                       # or: bash install.sh --workspace /scratch/you/csp
```

`install.sh` has no SLURM in it anywhere. It creates the two conda
environments both harnesses share (training: torch, jarvis-tools, ALIGNN
editable; scoring: pymatgen, `amd`, AtomBench editable — kept apart because
AtomBench's dependency pins can fight a working torch install), clones
AtomBench from GitHub, and writes `site.env` at the repo root with every path
it determined. Both harnesses' `env.sh` source `site.env` automatically if it
exists, so that one file is the entire porting step — neither harness's own
`env.sh` needs hand-editing to point at a new machine's paths.

What it deliberately leaves for you: the handful of scheduler-specific
values (account, partition, `--gres` syntax, GPU name, walltimes) that no
script can know without being told. `site.env` is written with each of these
as a commented-out placeholder, next to the exact `sinfo`/`sacctmgr` command
that answers it on your site.

After that, pick a harness, read its `PLAN.md`, and follow its own run order
(`00_setup.sh` → `preflight.sh` → `10_smoke.sh` → ...). `preflight.sh` in
each refuses to proceed while anything is unresolved.

```bash
bash install.sh --help          # every flag, and what each step of setup does
```

## Where the manuscript prose is

`current_manuscript` (untracked — a working LaTeX draft, not part of either
harness) is the paper these ablations feed. `HANDOFF.md` is written as a
narrative "what happened and why" for the first cluster move (2026-09-01→02)
and is worth reading for the traps it documents, even though `install.sh`
now automates most of what it describes doing by hand.
